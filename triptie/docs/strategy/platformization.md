# Стратегия платформизации

Этот раздел описывает текущие ограничения продукта на этапе MVP, потенциал выделения ядра в отдельный сервис и гипотетическую бизнес-модель для будущего масштабирования.

## MVP: почему сервис пока не может стать платформой

### 1. Нет уникального актива для продажи
- Вся ценность строится на оркестрации внешних данных: места (2GIS), карты (Яндекс/OSM), погода (Open-Meteo/Яндекс).
- Продукт агрегирует, фильтрует и визуализирует чужие данные. Это полезная логика, но не уникальный контент или запатентованная технология, за которую готовы платить B2B-клиенты.

### 2. Отсутствие сетевого эффекта
- Каждая поездка изолирована: данные одной группы не обогащают опыт другой.
- Пока нет общего каталога «проверенных маршрутов», системы рейтингов или социального графа, который можно монетизировать или продавать как data-продукт.

### 3. Ядро не выделено в отдельный сервис
- Генерация маршрута — часть бизнес-логики backend, а не независимый микросервис.
- Результат сильно зависит от контекста (город, даты, состав группы, погода), что усложняет стандартизацию API для внешних интеграторов.
- Требует прямых ключей к внешним API, что создаёт риски лицензирования при перепродаже.

### 4. Интерфейс — часть ценности
- Удобство продукта завязано на совместном редактировании, drag-and-drop локации, визуализации на карте.
- Если убрать фронтенд и оставить только API, останется «чёрный ящик», требующий глубокой документации и поддержки со стороны интегратора.

### Текущая модель: B2C
- Ценность создаётся напрямую для конечных пользователей (друзья, семьи, коллеги).
- Одна группа путешественников не создаёт ценности для другой группы → сетевой эффект отсутствует.
- Монетизация планируется через подписку для пользователей (Freemium/Premium).

## В будущем: что могло бы стать платформой

### Что необходимо улучшить
- **Точность алгоритма**: внедрение ML на основе истории реальных поездок и корректировок пользователей
- **Независимый кэш мест**: накопление собственных рейтингов, отзывов и атрибутов, снижающее зависимость от 2GIS/Яндекс
- **Аналитика и телеметрия**: сбор обезличенных данных о поведении пользователей, конверсии в бронирования, популярности локаций
- **Стандартизация API**: версионирование, SLA, песочница, биллинг, мониторинг

### Целевая аудитория (B2B)
| Сегмент | Потребность | Как TripTie Engine решает |
|---------|-------------|---------------------------|
| **Корпоративные тревел-отделы** | Автоматизация планирования командировок с досугом | Маршрут «офис + ужин + достопримечательности» под бюджет и предпочтения сотрудника |
| **Организаторы мероприятий** | Программа для участников на свободное время | Подборка мест рядом с площадкой с учётом временных окон между сессиями |
| **Онлайн-турагентства** | Дифференциация на конкурентном рынке | Персонализированная программа поездки как дополнение к бронированию отеля/тура |

### Гипотетическая модель монетизации
- **Подписка (SaaS)**: фиксированная плата за доступ к API + ежемесячный лимит запросов
- **Pay-per-use**: оплата за каждую успешную генерацию маршрута (для сезонных или разовых клиентов)
- **White-label + % от конверсии**: для стратегических партнёров, где маршрут ведёт к бронированию (требует прозрачной аналитики и доверия)

### Будущая модель: B2B2C
```
TripTie (мы) → Партнёр (турагентство / портал / корпорация) → Конечный пользователь
```
- **Выгода для нас**: рекуррентный доход, масштабирование через чужие аудитории, отсутствие затрат на прямой маркетинг
- **Выгода для партнёра**: уникальная фича без R&D, рост лояльности и среднего чека
- **Выгода для пользователя**: персонализированный маршрут «в один клик» внутри привычного интерфейса
